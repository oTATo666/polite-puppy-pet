**三个方案，按场景选**：

> 源库不动。三种模式：

> python dev/redact_db.py --mode strip-chat     # 只删聊天，保留事件
> python dev/redact_db.py --mode empty --demo   # 空库 + 3 条手写示例

**A 方案落地**（约 10 行）：

### P1-2 换包后双击，跑的还是旧版

**现状**：单实例用命名互斥体 `Local\PolitePuppyPet_SingleInstance`（`main.py` L1237）。检测到已有实例时，`summon_running_pet()` 会把**旧实例**的立绘唤到前台，然后新进程 `exit(0)`。

设计本身是对的（比旧版只弹"去托盘里找它"好），但有个副作用：**用户把新 exe 覆盖进去、双击，屏幕上出现小狗，他会以为新版跑起来了——其实内存里还是旧版进程。**

我这次测试就被卡住过：第一次启动新 exe，40 秒内没有任何新端口，进程直接退出。

**建议**（三选一，成本递增）：

1. **最小改动**：`/api/health` 返回里加 `version` 和 `exePath`；前端启动后请求一次，把版本显示在设置页底部。
2. **中等**：重复启动时弹一个原生对话框："已有实例在运行（版本 v1.0.29，路径 …），已为你唤回。要关掉它改用当前版本吗？" 选"是"就杀掉旧进程再起。
3. **彻底**：互斥体名字带上 exe 的哈希或版本号，不同版本允许并存（端口段 8765~8794 本来就有余量）。缺点是用户可能同时开两个小狗。

推荐 **2**，成本低、解决真问题。

### P1-3 混合措辞静默降级，出问题查不到

**现状**：`_brain_hybrid_on()`（L4091）默认返回 `True`（`BRAIN_HYBRID` 缺省为 `"1"`）。但走完 `_small_model_draft()` 拿不到草稿时，代码只是不设 `res["hybrid"]`，响应里就是 `hybrid: false`、`model: "local-brain"`，**不告诉你为什么**。

我实测 `BRAIN_HYBRID=1` 却拿到 `hybrid: false`，翻代码才知道是 `draft` 为空导致——`_small_model_draft` 里 model 为空就直接 `return ""`。

**建议**：加一个 `hybridReason` 字段，把四种情况区分开：

```python
# 情况：开关关闭 / 未配置 draftModel / 模型调用失败 / 草稿未通过人格闸门
res["hybridReason"] = "off" | "no-draft-model" | "draft-failed" | "rejected:<reason>"
```

前端在「设置 → 模型」底部显示一行灰字："混合措辞：未启用（未配置草稿模型）"。这样用户不用翻日志就知道该去配什么。

顺带：`_small_model_draft` 里那个 `except Exception: model = ""` 把异常吞掉了，建议至少 `log.debug` 一行。

### P1-4 本地大脑措辞质量

**实测表现**：问"你还记得我送你的小狗窝吗？"，她回了句"咋"。打分最高 4.6 的候选选出来是"不"，最后落到"咋"。

**三个可落地的改法**：

1. **长度下限**：对 `reply` 加约束，单字回复只在极短提问（"在吗""嗯"）时才允许，其余情况从候选中选长度 ≥ 4 的。现在的候选池里显然有更好的句子，只是没被选中。
2. **话题匹配权重**：`小狗窝` 在库里能查到（LIKE 命中 2 条），说明检索到了但没影响选句。建议把 `topic` 命中度作为独立权重项加进 `deliberate()` 的打分，而不是只靠情绪/策略分。
3. **兜底句库**：当最高分低于阈值（比如 < 6）时，不要硬选，用一句语义安全的话（"我记着呢""你说过的事我都记着"）兜底，比蹦一个"咋"体面得多。

**另外**：库里 `难受` 有 17 条、`开心` 66 条，但 1~2 字查询走的是 `LIKE '%词%'`（L1618）。这条路径本身是对的（我先前判断的"trigram 不支持短词"是误读，`FTS_MIN_LEN = 3` 已经处理了分流）。真正的问题是**全表 LIKE 无索引**，等记忆涨到十万级再优化，现在不用动。

## 3. P2：工程健壮性

### P2-1 `tools/` 两套路径解析，同一个坑会复发

这次 `voice_identity` 失效的根因不是漏打包那么简单，而是**两条路径并存**：

| 模块 | 路径来源 | 冻结后指向 |
|---|---|---|
| `memory_extract` | `exe_dir()/"tools"` | exe 旁边的真实目录 ✅ |
| `voice_identity` | `ROOT/"tools"` | `_MEIPASS` 临时解包目录 ❌ |

`ROOT` 在冻结后等于 `_MEIPASS`，往 `01_程序/tools/` 放文件 exe 根本看不见。

**建议**：统一一个 `app_root()`，所有"要读磁盘文件"的模块一律走它：

```python
def app_root() -> Path:
    if getattr(sys, "frozen", False):
        return Path(sys.executable).resolve().parent
    return Path(__file__).resolve().parent
```

然后全库搜 `ROOT /` 和 `Path(__file__).parent.parent`，逐个判断是"读包内资源"还是"读磁盘数据"——前者留 `_MEIPASS`，后者改 `app_root()`。这次只修了 `voice_identity`，同类隐患可能还有。

### P2-2 打包漏模块，且没有自检

`voice_identity.py`、`voice_profile.py`、`memory_extract.py` 都是**运行期才 import** 的（在函数体里 `import`），PyInstaller 静态分析扫不到，所以第一次打包全漏了。

**建议两步**：

1. **spec 里显式列全**（已经在 `PolitePuppy_voicefix.spec` 里做了，保留即可）：

```python
hiddenimports += ["voice_identity", "voice_profile", "memory_extract", "local_brain", "puppy_core"]
```

2. **加打包自检脚本** `pack_check.py`，打完包必跑：

```python
# 断言关键模块真的在 exe 里
import subprocess, sys
out = subprocess.run([sys.executable, "-m", "PyInstaller.utils.cliutils.archive_viewer",
                      "-l", "dist/PolitePuppy.exe"], capture_output=True, text=True).stdout
for m in ["voice_identity", "voice_profile", "memory_extract", "local_brain"]:
    assert m in out, f"漏打包: {m}"
print("打包自检通过")
```

更狠一点：打完包自动起实例、请求 `/api/voice/id` 和 `/api/memory/extract`，两个都 200 才算过。这次的两个 bug（漏模块 + 路径错）都能被这一步拦住。

### P2-3 运行时文件散落 exe 同级

现在 `01_程序/` 下会自己长出 `记忆/`、`.voice_cache/`、`agent_data/`、`plugins/`、`memory_diary.txt`。带来三个问题：

- 用户想备份，不知道该拷哪几个（说明文档里也写错了）
- 卸载要手动清四个地方
- 放在 OneDrive 里会被反复同步（`memory.db` 每聊一句就变，OneDrive 会不停上传）

**建议**：统一到一个数据根目录：

```python
def data_dir() -> Path:
    env = os.environ.get("POLITE_PUPPY_DATA")
    if env:
        return Path(env)          # 便携模式
    return app_root() / "data"    # 默认：exe 同级 data/
```

把 `记忆/`、`.voice_cache/`、`agent_data/`、`plugins/`、`memory_diary.txt` 全搬进 `data/`。首次启动做一次迁移：老路径存在且新路径不存在就 `shutil.move`，并在日志里记一行。

好处：备份=拷 `data/`，卸载=删 `data/`，OneDrive 用户可以把 `data/` 挪出去。

### P2-4 记忆检索的全表 LIKE

`FTS_MIN_LEN = 3`，1~2 字走 `WHERE text LIKE '%词%'`（L1618）。1.4 万条时是毫秒级，10 万条会明显变慢（每字都要扫全表，且 `count(*)` 是第二次全扫）。

**现在不用改**。等 `episodes` 超过 5 万条再做，届时两个方向：

- 建 unigram/bigram 辅助索引表（中文按字切）
- 或者短词查询只返回前 N 条并缓存计数（`total` 给个估算值即可，前端也不显示精确总数）
